# Работа шести участников

Каждый получает собственную локальную копию и собственную БД. Один процесс с общей БД неудобен: XSS сохраняется, роли и пароли меняются, отрицательные заказы влияют на показатели админки.

| Участник | Основное направление | Итог работы |
|---|---|---|
| Shmerkovich | Инъекции + debug, ошибки и раскрытие технологии | Доказать изменение SQL и утечки диагностических данных |
| Ulianov | Аутентификация и сессии | Правильные пароли, reset, session lifecycle |
| Hrustalev | Контроль доступа | Матрица anonymous/customer/admin × route |
| Shumkov | Браузер + CSP | Три XSS, CSRF, политика встраивания и Content Security Policy |
| Chikhladze | Файлы + SSRF/HTTP и кеширование | Границы файлов, загрузки, внутренних запросов и приватных ответов |
| Pryadko | Бизнес-логика + консоль и API | Цена, состав, идемпотентность, статусы и проверки API из терминала |

Категорий восемь: сеть и конфигурация разделены между Shmerkovich, Shumkov и Chikhladze, а консоль и API закреплены за Pryadko. [Точное распределение сценариев и отчёты](README.md#проверки-участников). Не все 57 слабостей независимы: записывайте общий корень, чтобы не считать один пропущенный middleware десятью разными находками в итоговом аудите.

## Формат отчёта о находке

```text
ID и название:
Предпосылки (роль, данные, состояние сессии):
Место: файл, функция, маршрут, параметр:
Обычный запрос и результат:
Изменённый запрос и результат:
Наблюдаемое доказательство:
Влияние, подтверждённое стендом:
Предполагаемое влияние в реальном магазине:
Первопричина:
Исправление:
Негативная проверка после исправления:
Проверка обычной покупки после исправления:
Оставшиеся ограничения:
```

Добавляйте дату, версию Node.js, проверяемый коммит и фактические результаты. Сохраняйте отчёты в `docs/reports/<user>/<reports>.md`. Исправления приложения и проверки выполняйте в отдельной локальной копии, а фрагменты кода и результаты включайте в отчёт. После локальных правок намеренно уязвимые assertions в `verify.mjs` должны падать для исправленных сценариев — создайте соответствующие новые проверки ожидаемого отказа, а не скрывайте результат.

## Как отправить отчёт прямо в main

Все участники имеют доступ на запись и работают непосредственно в `main`. Отдельные ветки и Pull Request для отчётов не нужны. Каждый изменяет только `.md` в своей папке `docs/reports/<user>/`; код, общие документы и чужие отчёты в коммит не включайте. Изолированные папки уменьшают вероятность конфликтов, но общая ветка всё равно требует синхронизации перед отправкой.

### Новая копия после замены истории

История начинается с `Initial commit`. Клонируйте репозиторий в новую папку. Из прежней копии переносите только свои несохранённые Markdown-отчёты; старую историю не объединяйте и старые коммиты не отправляйте.

```sh
git clone https://github.com/Danderety/RBPO-1.git lab-reports
cd lab-reports
```

### Подготовка

Команды подходят для PowerShell и Bash и выполняются из корня проекта. Ниже пример для `Shumkov`: замените имя на своё во всех путях и сообщениях. Регистр имени папки сохраняйте.

```sh
git status --short
git switch main
git pull --ff-only origin main
```

Начинайте с чистой рабочей копии. Если `status` показывает изменения, сначала сохраните нужные файлы отдельно и разберитесь с ними. При ошибке команды не переходите к следующему шагу.

### Изменения и коммит

Отредактируйте свой отчёт, затем подготовьте только конкретный файл:

```sh
git diff -- docs/reports/Shumkov/reports.md
git add -- docs/reports/Shumkov/reports.md
git diff --cached --name-only
git diff --cached
```

В индексе должны быть только ваши `.md` внутри `docs/reports/Shumkov/`. Для нескольких отчётов перечислите каждый путь в `git add --`. Не используйте `git add .`, `git add -A` или `git commit -a`. Случайно подготовленный файл снимите с индекса командой `git restore --staged -- путь/к/файлу`: его содержимое сохранится на диске. После этого повторите проверку.

```sh
git commit -m "Отчёт Shumkov: результаты лабораторной"
git status --short
git pull --rebase origin main
git diff --name-status origin/main...HEAD
```

Перед `pull --rebase` рабочая копия должна быть чистой. В последнем сравнении должны быть только ваши отчёты. После проверки отправьте коммит:

```sh
git push origin main
```

### Если другой участник успел отправить раньше

Если `push` отклонён с `fetch first` или `non-fast-forward`, получите новые коммиты, перенесите поверх них свои и повторите проверку и отправку:

```sh
git pull --rebase origin main
git diff --name-status origin/main...HEAD
git push origin main
```

Не используйте `--force` или `--force-with-lease` для обычной отправки отчётов: они могут затереть чужую работу. При конфликте в своём отчёте сохраните нужные изменения обеих сторон, уберите маркеры конфликта и выполните:

```sh
git add -- docs/reports/Shumkov/reports.md
git rebase --continue
```

После завершения rebase снова проверьте состав изменений и отправьте их. При конфликте в чужой папке или коде выполните `git rebase --abort` и разберите ситуацию с владельцем. Если GitHub сообщает о запрете прямой отправки или недостаточных правах, владелец должен проверить доступ и правила `main`; эта инструкция настройки GitHub не меняет.

`.gitignore` исключает сборки, настройки редакторов и локальные файлы, но не ограничивает права на папки и не исключает уже отслеживаемые файлы. Перед каждым коммитом проверяйте индекс.
