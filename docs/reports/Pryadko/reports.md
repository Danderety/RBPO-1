# Материалы проверок - Прядко Данила

## BIZ-01. Клиент сам назначает итоговую цену

После входа:

```js
await lab('/api/checkout', {
  total:-100,
  address:'Демо'
});
```

Если заказ создан с `total:-100`, сервер доверяет цене клиента.

- **Механизм:** `/api/checkout` записывает `Number(b.total)` без расчёта по каталогу.
- **Проверка после входа:** `await lab('/api/checkout',{total:-100,address:'Демо'})` создаёт заказ с отрицательной суммой.
- **Влияние:** недоплата; в настоящей платёжной интеграции возможны более серьёзные нарушения, но возврат реальных денег стенд не реализует.

- **Где:** INSERT в `/api/checkout`.
- **Лечение:** сервер получает только ID и количество, читает действующие цены, проверяет целое положительное количество, считает деньги в минимальных единицах, применяет разрешённые скидки. После исправления произвольный `total` не влияет на расчёт.

## BIZ-02. Несуществующий товар в заказе

```js
await lab('/api/checkout', {
  total:1,
  address:'Демо',
  items:[{
    id:999999,
    name:'Несуществующий товар',
    price:1
  }]
});
```

Если заказ создан, сервер не проверяет товары по каталогу.

- **Механизм:** `items` сериализуется в БД без проверки товаров, количества и согласованности с суммой.
- **Проверка:** `await lab('/api/checkout',{total:1,items:[{id:999999,name:'Несуществующий товар',price:1}],address:'Демо'})`; прочитайте созданный заказ через `/api/orders/<id>` и поле `items`.

- **Влияние:** заказы с несуществующими позициями, невозможность достоверной комплектации и учёта.
- **Где:** `JSON.stringify(b.items || [])`.
- **Лечение:** проверять существование товара и остаток, формировать снимок названия/цены на сервере, хранить нормализованные позиции с внешними ключами; пересчитывать итог. После исправления выдуманный ID отклоняется, корректная корзина сохраняется.

## BIZ-03. Повтор запроса создаёт дубликат

Дважды выполните один запрос:

```js
await lab('/api/checkout', {
  total:100,
  address:'Демо',
  items:[]
});
```

Если получены два разных `id`, защита от повторной отправки отсутствует.

- **Механизм:** каждый POST оформляет новый заказ, нет idempotency key.
- **Проверка:** дважды отправьте одинаковый `/api/checkout` и сравните разные ID в истории.
- **Влияние:** нежелательные дубли при повторе после сетевого сбоя. Два намеренных одинаковых заказа допустимы; проблема — отсутствие способа отличить их от повторной доставки одного запроса.

- **Где:** безусловный INSERT.
- **Лечение:** ключ идемпотентности, уникальность в рамках пользователя, транзакционное сохранение ответа, проверка совпадения тела при повторе ключа. После исправления один ключ даёт один заказ; новый ключ позволяет новую покупку.

## BIZ-04. Несуществующий статус заказа

```js
await lab('/api/admin/orders', {
  id:1,
  status:'teleported'
});
```

Проверьте:

```js
await lab('/api/orders/1');
```

Если статус `teleported`, сервер принимает любое состояние.

**Механизм:** поле `status` принимает любую строку, предыдущий статус не учитывается. **Проверка:** `await lab('/api/admin/orders',{id:1,status:'teleported'})`; значение видно через API. Можно также перевести `new` сразу в `shipped`. В UI неизвестный статус может отображаться пустым select — это симптом несогласованности модели.

- **Влияние:** обход процесса оплаты/отправки, недостоверный учёт
- **Где:** POST `/api/admin/orders`.
- **Лечение:** enum и явная машина состояний, проверка полномочий на переход, подтверждённая сервером оплата, транзакционное сравнение предыдущего статуса. После исправления неизвестная строка и запрещённый переход отклоняются даже для администратора.

## BIZ-05. Отрицательная цена товара

```js
await lab('/api/admin/products', {
  id:1,
  name:'Механическая клавиатура',
  price:-1
});
```

Обновите каталог. Если цена отрицательная, сервер не проверяет денежный диапазон.

- **Механизм:** админский API принимает нулевую или отрицательную цену, не проверяет диапазон и бизнес-условия.
- **Проверка:** войдите администратором и сохраните `-1` в цене товара, либо отправьте `/api/admin/products` с этим значением
- **Влияние:** каталог и обычная корзина используют ошибочную цену даже без подмены checkout.

- **Где:** POST `/api/admin/products`.
- **Лечение:** серверная схема данных, конечное целое значение в минимальных денежных единицах, разрешённый диапазон, аудит изменения. Проверка роли из ACCESS-04 обязательна отдельно. После исправления отрицательная цена отклоняется; корректная административная правка сохраняется и видна в каталоге.
