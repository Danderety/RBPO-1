# Инъекции: от пользовательского ввода к изменению поведения приложения

**Автор:** Shmerkovich · **Проект:** Faultline Shop · **Раздел:** 7 учебных сценариев инъекций


Инъекция возникает, когда приложение передаёт пользовательский текст другому интерпретатору и тот воспринимает его как часть инструкции. В этом стенде такими интерпретаторами выступают SQL-движок, табличная программа, средство просмотра журнала и браузер. Общая причина — отсутствие надёжной границы между данными и управляющей структурой.

## Карта исследования

Первые четыре сценария показывают изменение SQL: от обхода входа до чтения чужих заказов. Следующие три показывают, что безопасное сохранение строки в БД ещё не гарантирует безопасный экспорт или отображение.

| Сценарий | Точка входа | Что меняется | Ключевое доказательство |
|---|---|---|---|
| [SQL-01 · Обход входа](#sql-01) | `POST /api/login` → `email` | Условие проверки учётных данных | Роль `admin` при неверном пароле |
| [SQL-02 · Чтение пользователей](#sql-02) | `GET /api/products` → `q` | Источник строк выдачи | Email и пароли вместо полей товаров |
| [INJ-03 · Подмена поля отчёта](#inj-03) | `GET /api/report` → `field` | Вычисляемое SQL-выражение | Пароль администратора в `value` |
| [INJ-04 · Чужие заказы](#inj-04) | `GET /api/order-search` → `status` | Условие отбора по владельцу | Заказы нескольких пользователей в сессии Алисы |
| [INJ-05 · Формула в CSV](#inj-05) | Отзыв → экспорт CSV | Интерпретация содержимого ячейки | Формульный префикс `=` сохранён в CSV |
| [INJ-06 · Подделка журнала](#inj-06) | `POST /api/log` → `message` | Визуальные границы записей | Пользовательский перевод строки в сообщении |
| [INJ-07 · HTML-инъекция](#inj-07) | `GET /search` → `q` | Структура HTML-документа | Введённый тег отображается как заголовок |

Уровни риска ниже перенесены из исходных материалов как учебные оценки; это не расчёт CVSS. Раздел охватывает именно семь присланных сценариев. Debug, ошибки и раскрытие технологии из остальной части Shmerkovich сюда не включены.

## Подготовка стенда и фиксация результатов

В терминале из корня проекта запустите сервер (проект требует Node.js 24+):

```sh
npm start
```

Во втором терминале проверьте доступность:

```sh
node scripts/lab-cli.mjs health
```

Ожидаемый ответ:

```text
<<< STATUS 200
<<< BODY {"lab":"faultline-local-only","version":1}
```

Откройте `http://127.0.0.1:3000`, затем **F12 → Console** и один раз определите помощник:

```js
var lab = async (route, data) => {
  const response = await fetch(route, data === undefined ? {} : {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify(data)
  });
  const text = await response.text();
  console.log('STATUS', response.status, 'ANSWER', text);
  try { return JSON.parse(text); } catch { return text; }
};
```

`undefined` после определения функции — нормальный результат. Команды выполняйте по одному блоку. После обновления страницы функцию нужно определить снова. Запросы и ответы можно сохранить через **Network → Fetch/XHR → Payload / Response**; для перехода на `/search` смотрите запрос документа.

| Учебная учётная запись | Пароль | Исходное состояние |
|---|---|---|
| `alice@lab.test` | `alice123` | Покупатель, `id=1`, заказ № 1 |
| `bob@lab.test` | `bob123` | Покупатель, `id=2`, заказ № 2 |
| `admin@lab.test` | `admin123` | Администратор, `id=3` |

Значения относятся к начальным данным стенда. Если пароли, пользователи или заказы уже менялись, результаты могут отличаться. SQL-01 меняет текущую сессию, INJ-04 требует входа Алисой, INJ-05 и INJ-06 добавляют записи. Все примеры предназначены для этого локального учебного проекта.

Для итоговой сдачи укажите дату проверки, вывод `node --version`, проверяемый коммит (`git rev-parse --short HEAD`) и приложите фактические ответы. Сам по себе HTTP 500 не доказывает успешную инъекцию: нужно показать изменение смысла запроса или структуры вывода.

## SQL-01. Вход администратором без правильного пароля

**Риск:** критический. **Место:** `server.mjs`, обработчик `POST /api/login`, параметр `email`.

### Причина и влияние

Email и пароль напрямую включаются в запрос:

```sql
SELECT * FROM users WHERE email='<email>' AND password='<password>'
```

Кавычка в пользовательском вводе закрывает значение email, `OR id=3` добавляет альтернативное условие, а `-- ` комментирует оставшуюся проверку пароля. Сервер создаёт сессию выбранного пользователя. Влияние на стенде — получение административной сессии без знания пароля; в реальном магазине это угрожало бы операциям, доступным этой роли.

### Проверка

Выйдите из текущей сессии и подтвердите отказ для обычных неверных данных:

```js
await lab('/api/logout');
await lab('/api/login', {
  email: 'admin@lab.test',
  password: 'неверный'
});
```

Ожидается `STATUS 401`. Затем измените только email:

```js
await lab('/api/login', {
  email: "' OR id=3 -- ",
  password: 'неверный'
});
```

Ожидается `STATUS 200`, в JSON — `"role":"admin"`, в заголовках — установка cookie `session`. После обновления страницы должен появиться административный блок. Именно успешный вход при неверном пароле является доказательством.

### Исправление и повторная проверка

Искать пользователя параметризованным запросом `WHERE email=?`, затем отдельно проверять пароль библиотекой хеширования. Хранить хеши вместо открытых паролей и исключить пароль из ответа API. Простая замена кавычек не является общим решением.

После исправления инъекционный ввод и неверный пароль должны давать 401. Правильные данные должны по-прежнему создавать сессию с соответствующей пользователю ролью.
