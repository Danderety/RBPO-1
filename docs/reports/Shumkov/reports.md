## 1. CONFIG-03 — Отсутствие Content Security Policy
Предусловия
Приложение запущено локально.
Адрес приложения: http://127.0.0.1:3000.
Расположение
Файл: server.mjs
Функция: send()
Область: формирование HTTP-заголовков ответа.
Нормальный запрос
curl -i http://127.0.0.1:3000/
До исправления сервер возвращал HTTP-ответ без заголовка Content-Security-Policy.
Атакующий сценарий
Отдельный payload не требовался. Проверялось наличие защитной политики в HTTP-ответе.
Наблюдаемое доказательство
В исходной версии отсутствовал заголовок:
Content-Security-Policy
Подтверждённое влияние
Отсутствовала дополнительная браузерная защита, ограничивающая источники выполнения JavaScript и других ресурсов.
Реальное влияние
Отсутствие CSP увеличивает последствия XSS-уязвимостей, поскольку браузер не получает дополнительной политики ограничения выполнения скриптов.
Причина
В функции send() не устанавливался заголовок Content-Security-Policy.
Исправление
Добавлена политика:
default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
Negative check после исправления
curl -i http://127.0.0.1:3000/
 | grep -Ei 'HTTP/|content-security-policy'
Результат:
HTTP/1.1 200 OK
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
Результат: PASS

## 2. WEB-01 — Reflected XSS
Предусловия
Приложение запущено.
Доступен маршрут /search.
Расположение
Файл: server.mjs
Маршрут: /search
Параметр: q
Нормальный запрос
GET /search?q=test
Результат:
<h1>Результаты: test</h1>
Атакующий запрос
Использовался XSS-payload:
/search?q=<script>document.body.dataset.labXss='yes'</script>
До исправления содержимое параметра попадало непосредственно в HTML:
<h1>Результаты: <script>...</script></h1>
Наблюдаемое доказательство
Переданный JavaScript-код присутствовал непосредственно в HTML-ответе сервера.
Подтверждённое влияние
Пользовательский параметр URL позволял внедрять произвольную HTML/JavaScript-разметку.
Реальное влияние
Злоумышленник мог сформировать вредоносную ссылку, при переходе по которой JavaScript выполнялся бы в контексте приложения.
Причина
Параметр q выводился в HTML без контекстного экранирования.
Исправление
Добавлена функция escapeHtml(). Значение параметра q теперь экранируется перед вставкой в HTML.
Negative check после исправления
Проверены payload’ы:
<script>alert(1)</script>
и:
<img src=x onerror=alert(1)>
После исправления специальные символы выводятся в экранированном виде:
&lt;script&gt;alert(1)&lt;/script&gt;
Payload не интерпретируется как HTML/JavaScript.
Результат: PASS

## 3. WEB-02 — Stored XSS в отзывах
Предусловия
Пользователь авторизован.
Доступен API /api/reviews.
Расположение
Файл: public/app.js
Функция: reviews()
API: /api/reviews
Нормальный запрос
Отзыв с обычным текстом отправляется через /api/reviews и должен отображаться в списке отзывов как текст.
Атакующий запрос
В тело отзыва передавался payload:
<img src=x onerror="document.body.dataset.labXss='yes'">
До исправления содержимое отзывов выводилось через innerHTML.
Наблюдаемое доказательство
Вредоносный HTML сохранялся в базе данных и возвращался API /api/reviews.
До исправления он вставлялся в DOM через innerHTML.
Подтверждённое влияние
Вредоносный HTML сохранялся на сервере и мог отображаться другим пользователям.
Реальное влияние
Злоумышленник мог добиться выполнения JavaScript у пользователей, просматривающих страницу с вредоносным отзывом.
Причина
Данные отзывов вставлялись в DOM через innerHTML.
Исправление
Рендеринг отзывов переведён на безопасное создание DOM-элементов с использованием textContent.
Negative check после исправления
Ранее сохранённые вредоносные отзывы теперь выводятся как обычный текст,а не как HTML.
Небезопасный innerHTML для содержимого отзывов устранён.
Результат: PASS

## 4. WEB-03 — DOM XSS через URL Fragment
Предусловия
Пользователь открывает страницу с вредоносным fragment в URL.
Расположение
Файл: public/app.js
Функция: note()
Источник данных: location.hash
Атакующий запрос
Использовался fragment:
#note=%3Cscript%3Edocument.body.dataset.labXss%3D%22yes%22%3C%2Fscript%3E
До исправления данные из location.hash передавались в:
target.innerHTML
Наблюдаемое доказательство
Был выявлен следующий поток данных:
location.hash → decodeURIComponent() → innerHTML
Подтверждённое влияние
Данные из URL fragment могли попадать непосредственно в DOM без безопасного экранирования.
Реальное влияние
Специально сформированная ссылка могла использоваться для выполнения JavaScript в контексте приложения.
Причина
Использование innerHTML для данных, полученных из URL fragment.
Исправление
innerHTML заменён на:
textContent
Negative check после исправления
Проверка исходного небезопасного sink:
target.innerHTML
в обработчике note() не обнаружила его после исправления.
Результат: PASS

## 5. WEB-04 — CSRF через GET-запрос изменения адреса
Предусловия
Пользователь авторизован.
У пользователя существует заказ.
Сессионная cookie передаётся запросу.
Расположение
Файл: server.mjs
Маршрут: /api/address
Параметр: value
Демонстрационный маршрут: /lab/csrf
Нормальное состояние
До атаки адрес заказа Alice:
Учебная улица, 1
Атакующий запрос до исправления
curl -i -b cookies.txt \
"http://127.0.0.1:3000/api/address?value=CSRF-DEMO"
Результат:
HTTP/1.1 200 OK
{"ok":true}
После запроса адрес изменился на:
CSRF-DEMO
Наблюдаемое доказательство
Изменение состояния выполнялось через GET-запрос.
Подтверждённое влияние
Адрес заказа пользователя можно было изменить без отдельного подтверждения со стороны пользователя.
Реальное влияние
Сторонний ресурс мог инициировать нежелательное изменение состояния пользователя, если браузер отправлял его сессионные данные.
Причина
Операция изменения адреса была доступна через GET:
/api/address?value=...
Исправление
Изменение адреса переведено на POST:
POST /api/address
с JSON-телом:
{
  "value": "Новый учебный адрес"
}
Negative check после исправления
Старый GET-запрос:
curl -i -b cookies.txt \
"http://127.0.0.1:3000/api/address?value=CSRF-DEMO"
после исправления возвращает:
HTTP/1.1 404 Not Found
{"error":"Not found"}
Нормальный POST-запрос авторизованного пользователя возвращает:
HTTP/1.1 200 OK
{"ok":true}
Ограничение
Исправление закрывает конкретный GET-вектор, использованный в лабораторной работе. Полноценная защита production-приложения от CSRF должна также предусматривать CSRF-токены либо другой эквивалентный механизм защиты state-changing операций.
Результат: PASS для лабораторного сценария

## 6. WEB-05 — Отсутствие политики запрета встраивания
Предусловия
Приложение запущено.
Доступен адрес http://127.0.0.1:3000.
Расположение
Файл: server.mjs
Область: HTTP-заголовки функции send().
Нормальный запрос
curl -s -D - http://127.0.0.1:3000/
 -o /dev/null
До исправления ответ не содержал политики запрета встраивания.
Наблюдаемое доказательство
До исправления отсутствовали:
X-Frame-Options
и:
Content-Security-Policy: frame-ancestors ...
Подтверждённое влияние
Страница не имела явного ограничения на встраивание в iframe.
Реальное влияние
Это создавало условия для clickjacking-атак.
Причина
Отсутствовала политика frame-ancestors.
Исправление
В CSP добавлена директива:
frame-ancestors 'none'
Negative check после исправления
curl -s -D - http://127.0.0.1:3000/
 -o /dev/null | grep -i "Content-Security-Policy"
Результат:
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
Результат: PASS

## 7. WEB-06 — Open Redirect
Предусловия
Приложение запущено.
Доступен маршрут /redirect.
Расположение
Файл: server.mjs
Маршрут: /redirect
Параметр: next
Атакующий запрос до исправления
curl -i \
"http://127.0.0.1:3000/redirect?next=https%3A%2F%2Fexample.com"
Результат доисправления:
HTTP/1.1 302 Found
Location: https://example.com
Наблюдаемое доказательство
Приложение принимало произвольный внешний URL в параметре next.
Подтверждённое влияние
Сайт мог использоваться как промежуточный адрес для перенаправления пользователя на внешний ресурс.
Реальное влияние
Open Redirect может использоваться в фишинговых сценариях, когда ссылка начинается с доверенного домена приложения, но перенаправляет пользователя на сайт злоумышленника.
Причина
Параметр next использовался без проверки.
Исправление
Разрешены только внутренние абсолютные пути.
Внешние URL и значения вида:
https://example.com
отклоняются.
Negative check после исправления
/redirect?next=https://example.com
возвращает:
HTTP/1.1 400 Bad Request
{"error":"Invalid redirect"}
Normal check после исправления
Внутренний адрес:
/redirect?next=/
продолжает корректно возвращать:
HTTP/1.1 302 Found
Location: /
Результат: PASS

## 8. WEB-07 — postMessage без проверки origin
Предусловия
Страница содержит обработчик window.message.
Обработчик изменяет значение поля адреса.
Расположение
Файл: public/app.js
Обработчик: addEventListener('message', ...)
Проблема до исправления
Обработчик проверял тип сообщения:
if(event.data?.type==='set-address')
но не проверял источник сообщения event.origin.
Подтверждённое влияние
Сторонний отправитель мог передать приложению сообщение:
{
  type: 'set-address',
  value: '...'
}
Реальное влияние
При отсутствии проверки origin стороннее окно или iframe могло воздействовать на состояние интерфейса приложения.
Причина
Отсутствовала проверка доверенного источника сообщения.
Исправление
Добавлена проверка:
if(event.origin!==location.origin) return;
Теперь сообщения обрабатываются только от текущего origin приложения.
Negative check после исправления
Проверена логика обработчика.
Результат:
Trusted: MESSAGE-DEMO
Foreign: BLOCKED
Таким образом:
сообщение от доверенного origin обрабатывается;
сообщение от https://example.com
 блокируется.
Также выполнена синтаксическая проверка:
node --check public/app.js
Ошибок синтаксиса не обнаружено.
Ограничение
Проверка подтверждает корректность логики event.origin. Отдельная полноценная браузерная атака из внешнего origin в рамках этой проверки не выполнялась.
Результат: PASS
