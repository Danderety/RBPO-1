# Отчёт по анализу контроля доступа

**Участник:** Hrustalev\
**Направление:** Контроль доступа\
**Количество находок:** 7\
**Стенд:** `http://127.0.0.1:3000`\
**Среда:** локальный учебный стенд, SQLite fixture-данные, вымышленные
секреты, без внешней сети.

## Цель и методика

Цель --- проверить серверный контроль доступа и определить, может ли
пользователь читать или изменять данные без необходимых полномочий.

В текущем прогоне проверялись **anonymous** (без Cookie) и **customer** (Alice), а также состояние Alice после изменения роли на **admin**. Для каждой проверки фиксировались сессия либо её
отсутствие, HTTP-ответ, возвращаемые данные и фактическое изменение
состояния. Ответ `500` сам по себе не считался доказательством.

## ACCESS-01 --- IDOR чужого заказа

**Критичность:** высокая.

### Механизм

`/api/orders/:id` проверяет наличие сессии, но не владельца заказа.
Выборка выполняется по `id` без ограничения по `user_id`.

### Воспроизведение

Войти под Alice и выполнить:

![ACCESS-01: Alice авторизована как customer](screenshots/1.png)

*Рисунок 1 — исходное состояние: Alice (`alice@lab.test`) авторизована как `customer`; в кабинете отображаются её заказы.*

Открыть последовательно:

```text
/api/orders/1
/api/orders/2
```

[ACCESS-01: собственный заказ Alice: сохранённый HTTP-журнал](html/2.html)

*Доказательство 2 — `/api/orders/1` возвращает заказ с `user_id: 1`, соответствующий Alice.*

[ACCESS-01: чужой заказ Бориса: сохранённый HTTP-журнал](html/3.html)

*Доказательство 3 — при той же сессии `/api/orders/2` возвращает объект с `user_id: 2`, то есть заказ другого пользователя. Это подтверждает IDOR.*

Сравнить `user_id` в двух ответах.

### Наблюдаемое доказательство

При сессии Alice изменение номера заказа возвращает объект другого
пользователя.

### Влияние

Раскрытие истории покупок и персональных данных.

### Первопричина

Выборка вида `WHERE id=?` без проверки владельца.

### Исправление

Использовать `WHERE id=? AND user_id=?` либо централизованную объектную
политику с явным исключением для администратора. UUID не заменяет
проверку полномочий.

### Проверка после исправления

Alice видит свой заказ, но получает `403/404` на чужой. Администратор
получает доступ только по отдельной разрешённой политике.

## ACCESS-02 --- Административное чтение без входа

**Критичность:** критическая.

### Механизм

Административные GET-маршруты доступны без проверки сессии и роли.

### Воспроизведение

Без Cookie (отдельный анонимный HTTP-клиент) выполнить:

``` javascript
/api/admin/users
/api/admin/orders
```

[ACCESS-02: список пользователей доступен без входа: сохранённый HTTP-журнал](html/4.html)

*Доказательство 4 — без Cookie (отдельный анонимный HTTP-клиент) `/api/admin/users` возвращает записи пользователей и чувствительные поля без административной сессии.*

[ACCESS-02: список заказов доступен без входа: сохранённый HTTP-журнал](html/5.html)

*Доказательство 5 — без Cookie (отдельный анонимный HTTP-клиент) `/api/admin/orders` возвращает заказы разных пользователей без административной сессии.*

### Наблюдаемое доказательство

`HTTP 200` и приватные данные при отсутствии Cookie.

### Влияние

Массовая утечка пользователей, адресов и заказов; открытые пароли
усиливают ущерб.

### Первопричина

GET-маршруты `api/admin` не защищены общей серверной проверкой
административных полномочий.

### Исправление

Применить общий middleware `requireAdmin`, запрет по умолчанию,
фильтрацию полей ответа и тесты для anonymous/customer/admin.

### Проверка после исправления

Anonymous и customer получают `401/403`; admin --- только разрешённые
данные без паролей.

## ACCESS-03 --- Mass assignment профиля

**Критичность:** критическая.

### Механизм

Обычное обновление профиля принимает чувствительное поле `role`.

### Воспроизведение

```javascript
fetch('/api/profile', {method:'POST', headers:{'Content-Type':'application/json'}, body:JSON.stringify({name:'Алиса', role:'admin'})})
```

После запроса повторно получить `/api/me`; в текущем прогоне роль подтверждена этим запросом.


[ACCESS-03: Alice до изменения роли: сохранённый HTTP-журнал](html/access-03-before.html)

*Доказательство 6 — исходное состояние Alice: роль `customer`.*

[ACCESS-03: запрос mass assignment: сохранённый HTTP-журнал](html/access-03-request.html)

*Доказательство 7 — отправка `/api/profile` с `role:'admin'` HTTP-клиентом.*

[ACCESS-03: роль после запроса: сохранённый HTTP-журнал](html/access-03-after.html)

*Доказательство 8 — повторный GET `/api/me` показывает фактическую роль `admin`.*

### Наблюдаемое доказательство

Переданное пользователем поле `role` применяется сервером.

### Влияние

Повышение привилегий существующей учётной записи.

### Первопричина

`/api/profile` выполняет операцию вида `UPDATE users SET name=?,role=?`
без allowlist безопасных полей.

### Исправление

Разрешить обычному пользователю изменять только допустимые поля
(`name`); смену роли вынести в отдельную административную операцию.

### Проверка после исправления

Имя меняется, а передача `role` не меняет полномочия. Для возврата
учебного состояния использовать `role:'customer'` либо сбросить БД.

## ACCESS-04 --- Административная запись без полномочий

**Критичность:** критическая.

### Механизм

POST-маршруты изменения товара и заказа не проверяют сессию и роль.

### Воспроизведение

Без Cookie (отдельный анонимный HTTP-клиент):

```text
POST /api/admin/orders
{"id":1,"status":"shipped"}
POST /api/admin/products
{"id":1,"name":"Механическая клавиатура","price":1}
Content-Type: application/json; Cookie отсутствует
```


[ACCESS-04: анонимный административный POST-запрос: сохранённый HTTP-журнал](html/access-04-request.html)

*Доказательство 9 — административный POST выполняется без Cookie (отдельный анонимный HTTP-клиент).*

[ACCESS-04: состояние после неавторизованной записи: сохранённый HTTP-журнал](html/access-04-after.html)

*Доказательство 10 — фактическое изменение заказа либо каталога после анонимного запроса.*

### Наблюдаемое доказательство

Анонимные запросы изменяют заказ и каталог.

### Влияние

Повреждение заказов, цен и управления магазином.

### Первопричина

Административные SQL-операции записи выполняются без предварительной
серверной авторизации.

### Исправление

Проверять полномочия до SQL-записи, вести аудит автора операции и
отдельно валидировать переходы статуса и цены.

### Проверка после исправления

Анонимные и обычные пользовательские запросы не изменяют БД; разрешённые
административные операции проходят только после проверки роли и
бизнес-ограничений.

## ACCESS-05 --- Анонимное чтение объекта пользователя

**Критичность:** высокая.

### Механизм

`GET /api/users/:id` принимает числовой `id` и возвращает всю запись без
сессии.

### Воспроизведение

Без Cookie (отдельный анонимный HTTP-клиент):

``` javascript
/api/users/1
/api/users/2
```

### Наблюдаемое доказательство

Без Cookie возвращаются `email`, `role` и plaintext-пароль разных
пользователей.

[ACCESS-05: объект пользователя доступен без Cookie: сохранённый HTTP-журнал](html/access-05-user-object.html)

*Доказательство 11 — `GET /api/users/2` без Cookie возвращает `HTTP 200` и объект Бориса, включая `email`, `role` и plaintext-пароль.*

### Влияние

Неавторизованное раскрытие пользовательских данных, включая пароль в
открытом виде на учебном стенде.

### Первопричина

Нет проверки аутентификации/владения объектом, а ответ содержит
избыточные чувствительные поля.

### Исправление

Удалить публичный маршрут либо проверять `me.id === requestedId`/роль
администратора; формировать DTO без `password`.

### Проверка после исправления

Anonymous получает `401`; customer не читает чужой `id`; пароль
отсутствует даже в разрешённом ответе.

## ACCESS-06 --- Удаление чужого отзыва

**Критичность:** высокая.

### Механизм

Endpoint удаления не проверяет ни автора, ни администратора.

### Воспроизведение

```text
GET /api/reviews
```

Создать временный отзыв под Alice, запомнить его `id` и выполнить без Cookie:

```text
POST /api/reviews/delete
{"id":2}
```

После этого снова получить список.


[ACCESS-06: список отзывов до удаления: сохранённый HTTP-журнал](html/access-06-before.html)

*Доказательство 12 — исходный список отзывов; виден `id` выбранного отзыва.*

[ACCESS-06: анонимный запрос удаления: сохранённый HTTP-журнал](html/access-06-request.html)

*Доказательство 13 — `/api/reviews/delete` выполняется без Cookie (отдельный анонимный HTTP-клиент).*

[ACCESS-06: список отзывов после удаления: сохранённый HTTP-журнал](html/access-06-after.html)

*Доказательство 14 — повторный список показывает исчезновение временного отзыва №2, созданного Alice.*

### Наблюдаемое доказательство

Отзыв удаляется без подтверждения авторства или административных
полномочий.

### Влияние

Повреждение пользовательского контента.

### Первопричина

`POST /api/reviews/delete` не выполняет необходимую авторизацию. В
текущей схеме также отсутствует `user_id`, поэтому проверку владельца
нельзя добавить одним middleware.

### Исправление

Хранить автора, разрешать удаление автору/администратору и вести аудит.

### Проверка после исправления

Anonymous не удаляет отзывы; customer удаляет только свой; admin
действует по явно заданной политике.

## ACCESS-07 --- Export-route без авторизации

**Критичность:** критическая.

### Механизм

Отдельный export-route не включён в общую административную политику.

### Воспроизведение

Без Cookie (отдельный анонимный HTTP-клиент):

```javascript
/api/admin/export-orders
```


[ACCESS-07: export-route без административной авторизации: сохранённый HTTP-журнал](html/access-07-export.html)

*Доказательство 15 — `/api/admin/export-orders` возвращает данные без Cookie (отдельный анонимный HTTP-клиент), без административной авторизации.*

### Наблюдаемое доказательство

Endpoint возвращает защищаемые данные без административной авторизации.

### Влияние

Массовая выдача email, адресов и заказов.

### Первопричина

`GET /api/admin/export-orders` зарегистрирован вне защищённого
router/middleware. Скрытие ссылки или `admin` в URL не является
серверной авторизацией.

### Исправление

Регистрировать административные маршруты внутри защищённого
router/middleware и тестировать матрицу ролей для каждого нового
endpoint.

### Проверка после исправления

Anonymous/customer получают `401/403`; экспорт доступен только явно
разрешённой роли.
